## 三、三个运行的结果摘要

> 完整原始输出见各 `run*/terminal_output.txt`。**数字以实际跑出来的为准，本表只是索引。**

（2026-10-03 实测，原样记录）

| 运行 | 对象 | 扫描文件数 | 结果 | 退出码 | 报告位置 |
|---|---|---|---|---|---|
| run1 | `~/Desktop/赵怡涵_C1_提交包` | 192 | `✅ 29  ⚠️ 1  ❌ 0` | `0` | `run1_C1/packager_report.md` |
| run2 | `~/Desktop/赵怡涵_C2_提交包` | 37 | `✅ 29  ⚠️ 1  ❌ 0` | `0` | `run2_C2/packager_report.md` |
| run3 | `~/Desktop/赵怡涵_C4_提交包`（本包） | 49 | `✅ 31  ⚠️ 0  ❌ 0` | `0` | `run3_C4/packager_report.md` |

**两个 `⚠️` 都是真问题，不是误报**：

- **run1（C1）**：`README 六段必备 — 未检出小节：是什么、解决什么问题、示例`。打开 C1 的 README 看标题序列，确认它从 `# CS146S 中文课程资料包 · C1 提交` 直接跳到 `## ✅ Demo / 演示入口`，**真的没有"是什么 / 解决什么问题 / 示例"三节**——而《交付规范》§2 明确要求 README 含这六段。
- **run2（C2）**：`README 六段必备 — 未检出小节：是什么、解决什么问题`。同上，C2 的 README 也是从 `## ✅ Demo / 演示入口` 开始的。

**两条都是真实发现，不是误报。** 而且这暴露了一个共同模式：**写 README 时容易一头扎进"怎么用"，忘了先说"这是什么、解决什么问题"。** 这恰好是这个工具存在的意义——它是"别人"的视角，而作者自己看不出这个盲区。

> 顺带说明：run1 早期还报过 `方案设计 未检出"架构|结构"`，那条**是措辞差异引发的噪音**（C1 写的是 `## 3. 模块分解`），我据此把探针放宽成 `架构|结构|模块|分层|组件|流程|pipeline`。**能区分"真问题"和"噪音"，也是靠打开文件一个个看出来的。**

> 完整原始输出（含命令、扫描数、退出码）见各 `run*/terminal_output.txt`。

**为什么要拿真实包测**：开发过程中，正是这三个真实包暴露了 5 个 bug，其中一个是"自检器凭空发明了官方要求，冤枉了一个已合格的历史包"。如果只用造出来的假包演示，这些 bug 一个都发现不了。完整经过见 `赵怡涵_C4_AI日志.md`。
